## Awaria publikacji na GitHub Pages (run 38424779872) — naprawiona w repo

Zgłoszenie właściciela: po scaleniu PR #164 publikacja na Pages padała
(„Multiple artifacts named \"github-pages\" … Artifact count is 4").
**Workflow nie zmieniał się od miesięcy, a dziesięć poprzednich runów przechodziło
za pierwszym razem — to nie była regresja w repo.**

### Co się faktycznie stało

- **Próba 1 — wyścig:** upload `upload-pages-artifact` skończył się 15:50:09,
  `deploy-pages` ruszył 15:50:09 i zgłosił „No artifacts named \"github-pages\"
  were found" — świeżo wgrany artefakt nie był jeszcze widoczny w API (artefakt
  tej próby istnieje, `created_at` 15:50:09), a `deploy-pages@v4` nie ponawiał
  tego odczytu.
- **Próby 2–4 — kumulacja:** każdy RE-RUN dokłada w TYM SAMYM runie kolejny
  artefakt `github-pages`, a `deploy-pages` wymaga **dokładnie jednego**
  (`run_attempt: 4`). Awaria stała się samopodtrzymująca — „kliknij ponownie"
  mogło ją tylko pogłębić.

### Naprawa (jest już w repo, w `.github/workflows/pages.yml`)

1. `permissions: actions: write` + krok kasujący artefakty `github-pages`
   z poprzednich prób tego runu **przed** uploadem (przy pierwszej próbie nie ma
   czego kasować; przy re-runie czyści pole dla `deploy-pages`).
2. Krok czekający **między** uploadem a publikacją, aż świeży artefakt będzie
   widoczny na tej samej liście, którą czyta `deploy-pages` (maks. 20 × 3 s).
3. `deploy-pages@v4 → v5` — dokładnie ten pin, który wskazuje oficjalny szablon
   GitHub Pages; v5.0.1 ma backoff + jitter w odpytywaniu o gotowość, czyli leczy
   naszą klasę wyścigu u źródła. Reszta pinów (checkout@v4, setup-node@v4,
   configure-pages@v5, upload-pages-artifact@v3) **została jak w szablonie** —
   ostrzeżenia o Node 20 dla nich to informacja, nie awaria, a podnoszenie ich
   byłoby zmianą niemożliwą do sprawdzenia przed scaleniem.

Strażnik `test/ci-workflow-tiers.test.js` pilnuje żywego workflowu: obecność
`actions: write`, realny `DELETE` na API, kolejność sprzątanie < upload <
czekanie < deploy, brak „połowicznej" protezy i brak niezamkniętych znaczników
`PENDING-UPLOAD` (mechanizm wgrania wzorca zostaje w repo jako bezpiecznik —
opisany w `docs/setup/workflows/README.md`).

### Weryfikacja

- Mutacje (każda czerwieni): brak `actions: write` w żywym workflowie;
  kroki sprzątania bez uprawnienia; sprzątanie po uploadzie.
- RED→GREEN samej protezy: po cofnięciu regionów (git stash) 3/4 → z protezą 4/4.
- Składnia: YAML parsuje się (9 kroków w jobie `deploy`), oba skrypty `run:`
  przeszły `bash -n`, kwerendy `jq` uruchomione na żywym runie (sprzątanie
  widzi dokładnie 4 zaległe ids; pętla czekania poprawnie kończy się błędem
  przy liczbie ≠ 1, gdyby czegoś brakowało).
- Bramy: `npm test` 8134/8134, `npm run build` 74 moduły / 5108,5 kB.

### Co zostało dla właściciela

1. **Scal PR #165** — jego push do `main` uruchomi publikację nowym workflowem,
   który sam się posprząta i poczeka na artefakt. Żadnego ręcznego kopiowania
   plików już nie ma (Appka dostała uprawnienie `workflows`, więc agent wnosi
   zmiany w workflowach zwykłą drogą PR).
2. **Nie klikaj „Re-run" na starym runie 38424779872** — on ma już cztery
   artefakty i nawet z nowym workflowem (który sprząta tylko WŁASNY run) nie
   ma czego publikować; strona wstanie z nowego runu po scaleniu.
3. (Opcjonalnie) Cztery zaległe artefakty starego runu (`11827359673`,
   `11827919587`, `11828709835`, `11844826622`, po ~1,6 MB) są **nieszkodliwe**
   — `deploy-pages` czyta wyłącznie artefakty własnego runu. Można je skasować
   w UI (Actions → run → „Artifacts" → kosz) albo zostawić — wygasną same po
   90 dniach. Token agenta nie ma `actions: write`, więc DELETE z tej strony
   nadal zwraca 403 (sprawdzone); token workflowu ma `actions: write` (to on
   sprząta w trakcie publikacji).
