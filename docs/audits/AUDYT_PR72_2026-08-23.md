## N1 — debug `process.env` w bocie wywracał stół w przeglądarce (KRYTYCZNE)

W `scoreCommand` została instrumentacja z poprzedniej sesji:

```js
const finish = (score) => { const w = weightedScore(cmd.type, score);
  if (process.env.BOT_DEBUG_SCORES && cmd.objectId === 'slaad') console.error(…); return w; };
```

Trzy wady naraz:

1. **`process` nie istnieje w przeglądarce.** Sklejony artefakt (ADR 0011,
   `file://` na iPadzie właściciela) rzuciłby `ReferenceError` przy PIERWSZEJ
   wycenie ruchu bota — czyli przy pierwszym ruchu partii. Linia była już
   w `dist/mtg-table.html` (sprawdzone grepem na zbudowanym artefakcie).
   Testy w Node tego nie widzą (tam `process` jest globalny) — klasa L5.
2. **Rozpoznanie karty po ID w rdzeniu** (`cmd.objectId === 'slaad'`) — ADR 0002.
3. **Instrumentacja diagnostyczna w kodzie produkcyjnym** — `ENVIRONMENT.md` §3
   ostrzega dokładnie przed tą pułapką (debug znikający razem z fiksem).

**Fix:** przywrócenie `const finish = (score) => weightedScore(cmd.type, score);`

**Strażnik (generyczny, nie na jedną linię):** `test/m201-audyt-pr72.test.js`
skanuje KAŻDY moduł wchodzący do artefaktu (`collectModules`) i czerwienieje na
globalach Node (`process.`, `__dirname`, `__filename`, `require(`, `node:`),
na instrumentacji debug oraz na `process.env` w `dist/`. Mutacyjnie: 3/3 RED
przed fixem.

## N2 — „Whenever you're dealt combat damage” odpalało raz na atakującego

Gałąź `combat_damage_to_you` (dodana w PR #72 razem z fiksem M200/N3) odpalała
trigger na KAŻDYM zdarzeniu `damage_dealt` do gracza. Dwóch niezablokowanych
atakujących = dwa triggery Contested Game Ball na stosie.

**Weryfikacja u źródła przed zmianą (L57)** — ruling WotC 2023-11-10:
*„Contested Game Ball's triggered ability triggers only once whenever you're
dealt combat damage, no matter how many creatures deal combat damage to you at
the same time.”* Obrażenia bojowe są zadawane jednocześnie (CR 510.2), a
strumień zdarzeń jest per źródło — grupowanie należy do skanu triggerów.

**Fix:** zbiór `combatDamagedPlayers` per komenda (wzorzec z tego samego pliku:
Disa the Restless / `anyCombatDamageControllers`).

**Testy (3, RED→GREEN):** jeden trigger przy dwóch atakujących; anty-over-fix
„jeden atakujący nadal odpala”; anty-over-fix „nowa walka = nowy trigger”.

## O2 — obserwacja: moment wygaśnięcia zakazu blokowania

`turn.cantBlockRestrictions` (M200/L) jest zerowane przy TWORZENIU nowej tury,
a nie w kroku cleanup (CR 514.2). Różnica jest niewidoczna w grze — w krokach
`end`/`cleanup` nie deklaruje się bloków — więc zostaje jako obserwacja, nie
zmiana. Reszta rozwiązania (efekt ciągły czytany read-time przez centralny
`creatureCantBlock`, obecność w odcisku stanu przez `turn`, opis zdarzenia
`turn_cant_block`) jest zgodna z CR 611.2 i z L55.

  wyłącznie komendy DODAJĄCE manę do puli decydującego gracza; rodzina trzech

  nałożony też na ścieżkę „jednoczesnych zgonów”.
